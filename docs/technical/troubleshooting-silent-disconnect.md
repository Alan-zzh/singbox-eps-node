# 闪断排查手册

**适用场景**：用户反馈“网页能开，但聊天/私信/发消息发不出去，过一阵又恢复”，怀疑是代理节点、CDN、服务器、客户端或路由器问题。

---

## 先看结论

这类问题**不一定是代理闪断**。如果症状主要集中在：

- X / 推特私信
- 短时间内连续发消息
- 页面浏览、普通网页打开、测速、其他网站访问基本正常

要优先怀疑：

- **平台侧风控/限流**
- **账号短期限发**
- **会话级阻断**

不要一上来就默认是：

- 服务器炸了
- CDN 优选错了
- Reality / WS / Trojan / HY2 协议坏了

---

## 这次排查得到的关键信号

本次案例里，最终最值得优先怀疑的是：

1. 症状主要出现在 **推特私信发送**
2. 用户能正常上网页，其他行为不一定同步异常
3. “过一阵又恢复”符合平台侧风控冷却特征
4. 即使切换不同节点、不同模式，体感上也可能类似

这意味着：

**“消息发不出去”不能直接等价于“代理线路断了”。**

---

## 本次排查与修复时间线

下面这段专门记录这次为了排“闪断”做过的关键回退、修复和判断，后面再排查时可以直接对照，避免重复走弯路。

### 已核过的主要方向

1. **健康检查周期性重启**
   - 曾怀疑 `health_check.sh` 因内存不足反复重启服务
   - 后续核实最近日志里并没有持续命中“内存紧张→重启”分支
   - 这条线最终不是主根因

2. **固定节点 keepalive / TFO / 激进 TCP 参数**
   - 回退过固定节点上的 `tcp_keep_alive`
   - 回退过 `tcp_keep_alive_interval`
   - 回退过 `tcp_fast_open`
   - 目的是排除“半死连接/无感断线”的公共放大器

3. **Clash 自动选择高风险参数**
   - 去掉过：
     - `keep-alive-interval`
     - `tcp-concurrent`
     - `unified-delay`
   - 并保留 Clash url-test 黄金参数：
     - `lazy: false`
     - `tolerance: 150`
     - `interval: 60`
     - `url: http://cp.cloudflare.com/generate_204`
     - `timeout: 5000`

4. **CDN 优选链路 Bug**
   - 修过 CDN 换 IP 逻辑异常
   - 修过 403 误判导致候选池被清空
   - 修过评分排序、信号刷新、优选分配等问题
   - 也做过 `domain_default` 回退，先排除 CDN 优选干扰

5. **系统层优化**
   - 核过两台机的 keepalive / qdisc / BBR / sysctl / conntrack
   - 当前判断是：这类系统优化会同时影响所有协议，因此排查时必须单独看待

6. **客户端与本地环境污染**
   - 核到过宿主机存在：
     - 系统代理残留
     - Clash Verge 后台
     - mihomo 本地监听
     - 本地 DNS / fake-ip 接管
   - 因此宿主机体感不能直接当作“服务器故障证据”

7. **爱快路由器侧**
   - 核到过 QoS / 智能流控是高风险项
   - 曾出现“关闭后明显改善”的情况
   - 所以它仍然是长期排查优先级很高的共因

### 当前最大的修正认知

这次最重要的修正不是某一行代码，而是判断顺序：

**“推特私信发不出去”本身不能直接证明线路闪断。**

如果症状只集中在推特私信、短时间高频发消息、过一阵自动恢复，就必须先排平台风控/限流。

## 排查顺序

### 第 1 步：先区分“平台限制”还是“链路故障”

优先做这几个动作：

1. 同时测试：
   - 打开普通网页
   - 打开 X / 推特时间线
   - 发送私信
   - 访问另一个非推特的需要实时交互的网站
2. 如果只有推特私信失败，而网页浏览基本正常：
   - 优先怀疑平台风控
3. 如果多个网站的实时交互都一起异常：
   - 再怀疑代理链路或本地网络

### 第 2 步：做“非推特对照”

不要只拿推特当唯一判断标准。至少补 1 个对照：

- Telegram / Discord / WhatsApp Web / Gmail Chat / 任意其他实时站点

判断：

- 如果只有推特私信异常：更像平台限制
- 如果所有实时通讯都异常：更像网络或代理问题

### 第 3 步：看是否具备“限流特征”

更像推特风控/限流的特征：

- 短时间连续发消息后开始失败
- 失败一段时间后自动恢复
- 浏览、刷新、看时间线仍基本正常
- 换节点后不一定立刻恢复
- 同一账号在不同节点上仍可能复现

更像代理/线路故障的特征：

- 多个网站同时卡
- 整体网页加载都明显异常
- 长连接、下载、测速、API 请求一起抖
- 服务器日志中有同步的 `EOF / timeout / reset / invalid connection`

---

## 平台限流与代理故障的区别

| 现象 | 更像平台限流 | 更像代理故障 |
|------|--------------|--------------|
| 只有推特私信异常 | 是 | 否 |
| 网页打开正常 | 常见 | 不典型 |
| 过一阵自己恢复 | 常见 | 也可能，但不够特异 |
| 换节点后仍一样 | 常见 | 也可能 |
| 服务器日志无同步异常 | 常见 | 不支持代理故障 |
| 多站点一起异常 | 否 | 是 |

## 本项目侧固定检查项

即使怀疑是平台限流，也要先把下面几项核清楚，避免误判。

### 1. 订阅模式

确认当前是否在简化基线：

- `CDN_MODE=domain_default`
- `singbox-cdn` 已停用
- CDN 节点回到域名基线

这样可以先排除：

- CDN 优选 IP 分配
- 自动刷新
- 用户路径评分

如果要恢复“最佳自动切换 + CDN 优选”运行态，目标应切回：

- `CDN_MODE=ip_optimized`
- `singbox-cdn` 启用并运行
- Clash 继续保持合规 url-test 参数
- `MATCH -> 节点选择`
- `节点选择` 首项为 `自动选择`

### 2. 客户端自动选择放大器

Clash 配置必须保持：

- `lazy: false`
- `tolerance: 150`
- `interval: 60`
- `url: http://cp.cloudflare.com/generate_204`
- `timeout: 5000`
- `MATCH -> 节点选择`
- `节点选择` 首项必须是 `自动选择`

并避免恢复这些高风险项：

- `keep-alive-interval`
- `tcp-concurrent`
- `unified-delay`

### 3. 固定节点回退状态

固定节点应优先保持保守配置：

- 不额外写 `tcp_keep_alive`
- 不额外写 `tcp_keep_alive_interval`
- 不额外写 `tcp_fast_open`
- `multiplex.enabled: false`

### 4. 服务端日志对照

若怀疑真闪断，必须同时对照：

- `singbox` 是否重启
- 最近是否有：
  - `EOF`
  - `timeout`
  - `reset`
  - `processed invalid connection`

如果用户体感异常时，日志没有同步异常，平台侧问题的可能性会上升。

## 本机与路由器检查项

### 本机

先确认不是脏环境：

- 系统代理是否还开着
- Clash / mihomo 是否仍在后台
- 本机 DNS 是否被 fake-ip / 本地代理接管
- 虚拟网卡 / VMware / WSL / Docker 是否改了 DNS 或转发

### 路由器

优先排查：

- QoS / 智能流控
- 会话保持
- 出口策略
- DNS 接管

这次案例里，爱快 QoS 关闭后曾出现明显改善，因此：

**路由器流控仍然是长期排查中的高优先级项。**

---

## 推荐的最小判定流程

以后遇到同类问题，按这个顺序来：

1. 先测普通网页是否正常
2. 再测推特私信是否异常
3. 再测一个非推特实时应用
4. 同时看服务器日志是否有同步异常
5. 如果只有推特私信异常，优先判平台限流
6. 如果多站点实时应用一起异常，再查代理链路

---

## 从保守基线恢复到最佳状态的顺序

如果已经为了排查退回了保守模式，不要一次性乱加，建议按这个顺序恢复：

1. `domain_default`
   - 验证基础协议是否稳定
2. `domain_optimized`
   - 验证域名优选是否稳定
3. `ip_optimized + singbox-cdn`
   - 恢复完整自动优选
4. Clash 保持自动切换
   - 但必须使用合规黄金参数，不再恢复激进保活项

### 当前推荐的“最佳状态”

在本项目里，当前推荐的目标态不是“极限压榨”，而是：

- CDN 自动优选开启
- Clash 自动切换开启
- 固定节点保守
- 不恢复 `keep-alive-interval` / `tcp-concurrent` / `unified-delay`
- 不恢复额外 `tcp_keep_alive*` / `tcp_fast_open` 到固定节点

也就是：

**保留自动切换与 CDN 最优能力，但去掉已知高风险放大器。**

---

## 当前建议

对于“网页正常，但推特私信一阵一阵发不出去”的情况，当前建议是：

1. 先不要再把推特私信单独当成代理故障证据
2. 必须加一个非推特实时应用做对照
3. 若短时间高频发消息后失败，优先按平台风控处理
4. 只有在多站点实时交互都异常时，才继续往服务器/协议/网络层深挖

---

## 一句话经验

**“发不出推特私信”先判平台限流，再判代理闪断；不要只凭单一应用体感就改服务器。**
